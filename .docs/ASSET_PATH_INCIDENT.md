# アセットパス 404 障害 — 再発の構造と恒久対策

`vite.config.ts` の `base` 設定に起因して **全ツールが白画面になる** 障害が、2026-03 以降くり返し発生している。
この文書はその再発構造・過去の対策がなぜ効かなかったか・今後の判定手順をまとめた正本。

同じ症状を見たら、まず「診断手順」だけ読めばよい。

---

## 症状

- `https://tools.elchika.app/<app>/` を開くと**真っ白**（またはツールが表示されない）
- **HTML は HTTP 200 で正常に返る**。壊れているのは HTML が参照する JS/CSS

```
GET /home/                          → 200 text/html   ← 正常に見える
  └─ 参照 /assets/index-xxx.js      → 404             ← 本当の障害
     実体の場所 /home/assets/index-xxx.js → 200
```

JS が読めないので `<div id="root">` が空のまま残り、白画面になる。

**この症状はステータスコードだけを見る監視では絶対に検知できない。** 後述のとおり、実際に検知器が空振りした。

---

## 原因

各アプリの `vite.config.ts` の `base` 設定。

| 設定 | ビルド後の参照 | 結果 |
|---|---|---|
| `base: '/'` | `/assets/index-xxx.js`（絶対） | ❌ 404。実体は `/<app>/assets/` にある |
| `base: './'` | `./assets/index-xxx.js`（相対） | ✅ `/<app>/` 配下で正しく解決される |

このリポは **1 つの Workers で `/<app>/` サブパス配信**する構成のため、`base` は必ず `'./'` でなければならない。
`base: '/'` は「サイトのルートに単独のアプリを置く」場合の設定であり、この構成とは両立しない。

### 再発が続いた 2 つのループ

**ループ 1: 新規アプリが `base: '/'` を持ち込む**

テンプレートおよびコピー元（`url-encoder` が事実上の雛形）が `base: '/'` だったため、
一括修正しても新しいツールを追加するたびに壊れた設定が増えていった。
→ `da2ec2b1` で `templates/react-spa` が `'./'` になったため、**この流入経路は塞がっている**。

ただし `create-app.js` はもう 1 つ `templates/app` を参照する分岐を持つ（`useReactTemplate` が false のとき）。
こちらは `vite.config.ts` を含まないレガシーテンプレートなので、
**このテンプレート経由で作った場合は `base` を手書きすることになり、`'/'` が混入しうる**。

**ループ 2: 対症療法が再ビルドで巻き戻る**

`2d49993c` は発生源の `vite.config.ts` を直さず、**ビルド成果物の `index.html` を後から書き換えた**。
`packages/router/public/` はビルド生成物なので、次に誰かが `build-all.sh` を回した瞬間に
`base: '/'` から再生成され、修正が丸ごと消える。

2026-07-29 の障害はまさにこれ。git の状態がそれを示していた：

```
HEAD の public/*/index.html         : 329 件すべて "./assets/..."  ← 対症療法後の状態
working tree の public/*/index.html : 169 件が "/assets/..."       ← 再ビルドで巻き戻った
本番が配信していた内容              : "/assets/..."                ← 巻き戻った状態がデプロイされた
```

## 過去の対策がなぜ効かなかったか

### 1. 検知器の合格条件が症状とすれ違っていた

`scripts/health-check-runtime.js` の判定は以下だった。

- HTTP ステータスが 200 か
- `content-type` が `text/html` か
- body に `<html` が含まれるか

**壊れている状態はこの 3 条件をすべて満たす。** HTML 自体は完全に正常に配信されるからだ。
その結果、全アプリが白画面でもヘルスチェックは「正常」を報告し続けた。

> 教訓: 検知器を作ったら「**壊れている状態を実際に入力して、ちゃんと落ちるか**」を確認する。
> 正常系しか通していない検知器は、沈黙が「異常なし」なのか「見えていない」なのか区別できない。

### 2. 修正を発生源ではなく生成物に当てた

前述のループ 2。ビルド生成物への修正は、次のビルドで必ず消える。
`packages/router/public/` は成果物なので、**恒久修正は必ず `apps/*/vite.config.ts` 側に入れる**。

### 3. 一括修正の対象が「今回追加分」に限定されていた

`bc6d1534` は新規 11 アプリだけを修正し、既存 168 件を残した。
`base` はリポ全体で 1 つの値に揃うべき不変条件なので、**修正は常に全アプリを対象に、件数を数えて確認する**。

### 4. CI がビルドを行わない

`.github/workflows/deploy.yml` は `main` への push で `wrangler deploy` を実行するのみで、
`scripts/build-all.sh` を実行しない。つまり **`packages/router/public/` にコミットされた成果物がそのまま本番になる**。

このため、ローカルで壊れた状態をビルドしてコミット／デプロイすると、そのまま本番が壊れる。
逆に言えば、コミットされている `public/` の中身が本番の中身である。

## 診断手順（同じ症状を見たとき）

`curl` でステータスだけ見ても正常に見えるので、**HTML が参照しているファイルを実際に取得する**こと。

```bash
# 1. HTML が何を参照しているか
curl -s https://tools.elchika.app/home/ | grep -o -E '(src|href)="[^"]*"'

# 2. その参照先を実際に取得する（ここが 404 なら本障害）
curl -s -o /dev/null -w '%{http_code} %{content_type}\n' \
  https://tools.elchika.app/assets/index-xxxxx.js

# 3. リポ全体で base の値を数える（'./' 以外が 1 件でもあれば異常）
grep -h -E "^\s*base\s*:" apps/*/vite.config.ts | sed -E 's/^\s+//' | sort | uniq -c

# 4. ビルド成果物に絶対参照が混じっていないか（0 件が正常）
grep -l -E '(src|href)="/assets/' packages/router/public/*/index.html
```

判定に使う数字（2026-07-29 時点、アプリ数 346）:

- `apps/*/vite.config.ts` の `base` は **346 件すべて `'./'`**
- `public/*/index.html` の参照は **692 件すべて `./assets/...`**（1 アプリあたり JS + CSS の 2 件）

---

## 恒久対策

### 実施済み（2026-07-29）

- `apps/*/vite.config.ts` 全 346 件を `base: './'` に統一（発生源の修正）
- 全アプリ再ビルド → デプロイ → 全 346 アプリで参照アセットの実取得を確認
- テンプレート `templates/react-spa/vite.config.ts` は `'./'`（`da2ec2b1` 済み）＝新規アプリからの流入経路は閉じている

### 検証の作法（この障害に対して有効な確認方法）

デプロイ後の確認では、**HTML のステータスコードやバンドルハッシュの一致だけを根拠にしない**。
ハッシュが一致していても参照パスが間違っていれば白画面になる。
必ず「HTML が参照している URL を実際に GET して、200 かつ content-type が JS/CSS であること」まで見る。

`content-type` まで見るのは、SPA フォールバックを持つルーターが存在しないパスに対しても
HTML を 200 で返しうるため。`/assets/foo.js` に `text/html` が返ってきたら実体が無いサインである。

### 機械による再発防止（2026-07-29 導入）

文書だけでは止められないと判断した。過去 2 回とも担当者は問題を認識した上で直し方を誤っており
（生成物を直した／今回追加分だけ直した）、注意喚起は既に機能しなかった実績がある。
そのため以下を機械で止める形にした。

**1. 静的ゲート `scripts/check-asset-paths.js`**

ネットワーク不要。以下を検査し、違反があれば exit 1。判定できなかった場合も exit 1（ゲートなので fail-closed）。

- `apps/*/vite.config.ts` の `base` が `'./'` か（未指定・ファイル欠落も違反として扱う）
- `packages/router/public/*/index.html` が絶対パス `/assets/` を参照していないか
- その参照先ファイルが実在するか

```bash
node scripts/check-asset-paths.js                # すべて検査
node scripts/check-asset-paths.js --config-only  # vite.config のみ（ビルド前用）
```

**2. ビルド前ゲート（`scripts/build-all.sh`）**

先頭で `--config-only` を実行する。壊れた設定のまま**成果物を作ってしまうこと自体**を防ぐ。

**3. デプロイ前ゲート（`.github/workflows/deploy.yml`）**

`wrangler deploy` の直前で全検査を実行する。
このワークフローはビルドを行わずコミット済みの `public/` をそのまま配信するため、
壊れた成果物がコミットされていればここで止まる。

**4. ランタイム検知の強化（`scripts/health-check-runtime.js`）**

HTML が参照する JS/CSS を実際に GET し、200 かつ content-type が JS/CSS であることまで判定するようにした。
従来の「200 + text/html + `<html` を含む」だけでは本障害を検知できなかった（前述）。

検知能力は、障害と同じ形の HTML（`/assets/...` 絶対参照）を入力して
実際に 404 を検出すること・正常な HTML では誤検知しないことを確認済み。
検査関数は `module.exports` から取り出せるので、検知器自体のテストが書ける。

### 残っている穴

- `create-app.js` の `templates/app` 分岐は `vite.config.ts` を含まないため、
  そこから作ると `base` が手書きになる。ただし作成後に `check-asset-paths.js` が
  「base が未指定」として違反を出すので、ビルド／デプロイ前に止まる。
